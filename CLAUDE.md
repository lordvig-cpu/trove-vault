# TroveVault: project conventions

A universal collections app (Next.js 16, React, Tailwind 4, Supabase). Users define collections of
items, and design their own item templates in a visual layout builder. Read `AGENTS.md` (imported
above) before writing Next.js code; do not edit it, `next dev` regenerates it.

[`PROJECT_MAP.md`](PROJECT_MAP.md) is a one-line-per-file index of what every source file is
responsible for. Check it before hunting for where something lives, and update it in the same
commit whenever you add, remove, split or rename a file — it goes stale otherwise.

## Running and checking

- Dev server: `npm run dev` (port 3000). Type check: `npx tsc --noEmit`. Lint: `npm run lint`
  (currently clean; keep it that way).
- Tests: `npm run build` first, then `npm test`. Playwright runs against a production build on port
  3100 using the Edge channel. Some tests are `test.fixme` because they need seeded data.
- For any UI change, look at it in the browser (Playwright with `channel: 'msedge'` against the dev
  server) before calling it done. For refactors, compare before/after screenshots and computed styles.
- Never commit `next-env.d.ts` (generated). Use conventional commit messages (`feat:`, `fix:`,
  `refactor:`, `chore:`, `test:`) and small, focused commits.
- Line endings are LF everywhere (`.gitattributes`, `.editorconfig`).

## Code conventions

- **Naming:** the shared tree-view UI is called "Tree" (`TreeSubMenu`, `useTreeActionMenu`,
  `tree-*` CSS classes, `--tree-*` theme variables). The old "Explorer" name is gone; do not
  reintroduce it. The Items panel's dock id is `'items'`. The gear-icon popup shell itself is
  `TreeSubMenu` (not `TreeActionMenu` -- renamed because it's just as often an Actions +
  Properties menu as an Actions-only one); `useTreeActionMenu` is a separate, unrenamed hook
  (open/close/position state) that both kinds of menu call, so its name doesn't imply Actions-only.
- **Naming, template editor tabs:** the `template_hierarchy` dock content (`TemplateHierarchyTree.tsx`)
  is labeled "Layout" in the UI; the old "Structure" name is gone, don't reintroduce it. The
  `template_editor` dock content (`TemplateBlueprintTree.tsx`) is labeled "Blueprint"; the older
  "Content" and "Inspector"/"Template Inspector" names are gone too. There is no Components palette (the old
  `template_builder` bottom-panel dock content, once "Layout Builder"): its pre-defined blocks are in the Add menus,
  its simple templates in the bottom toolbar's Apply: pulldown, and its Row / Column / split primitives were the same as
  Add and Split. Edit Template docks nothing in the bottom panel, which holds Grabbed Content only. There is no docked "Properties" panel any more (the old
  `template_properties` tab / `TemplatePropertiesInspector.tsx` was removed): a node's properties live
  in its gear flyout's Properties tab and in the toolbars. Don't bring back a second place to edit them.
- **Icons:** SVG components in `components/icons/`, not emoji or unicode symbols. The only emoji
  left are user data: a template's own chosen icon (default 📦) and the item-type/virtual-category
  icons `UnifiedTree.tsx` and `lib/treeUtils.ts` derive from it.
- **Colors:** never write a hard-coded hex/rgb/hsl color in a component or a new CSS rule, not even
  temporarily. That includes Tailwind's stock palette classes (`text-slate-400`, `bg-amber-500/10`, ...),
  which are fixed colors: use the theme-backed Tailwind names registered in `app/globals.css`'s `@theme`
  blocks (`text-content-muted`, `bg-surface-hover`, `border-border-subtle`, `text-accent-secondary`,
  `bg-shade/40`, `text-danger-text`, `text-ok-text`, ...), adding a name there when a role is missing. The only
  fixed colors allowed are true constants (#000 / #fff where a theme needs pure black or white). Every color is a theme CSS variable. `--primary-accent` is the blue, `--secondary-accent`
  is the amber; shared text/surface/border roles have their own prefixes (see
  `app/styles/themes/OKLCH.md`). Component styles consume the readable aliases in
  `app/styles/themes/theme-semantic.css`, which map to `theme-oklch-dark.css` / `theme-oklch-light.css`.
  If a rule needs a color role that has no alias yet, add it to `theme-semantic.css` for both
  `:root` (dark) and the light-mode override, backed by an existing `--oklch-blue`/`--oklch-yellow`
  derived token — don't invent a new literal color. The OKLCH recipe itself
  (`theme-oklch.css`) is generated by `scripts/generate-oklch-theme.mjs` from `theme-premium-contrast.css`;
  only touch it through the generator, and only when recalibrating the base palette, not for a single
  new alias.
- **Data access:** all database access goes through `lib/data/*` (items, collections, templates,
  templateFields, workspace); hooks and components never import `supabase`. A save either fully
  succeeds or cleans up after itself (e.g. `createItem` deletes the item and the uploaded photo if a
  later step fails). Components do not import `supabase` directly. The client is typed by
  `types/database.ts`, hand-written from `.supabase/schema.sql` in the Supabase CLI's generated shape
  (regenerate it when the CLI is set up); convert rows to the app's own types with the mappers in
  `lib/data/mappers.ts`, never with casts.
- **Item forms:** the Create and Edit item modals share `hooks/useItemForm.ts` and the
  `components/item-form/*` pieces (`ItemModalShell` keeps the error and buttons in view).
  Editing an item is the main way users manage its values, so the edit form (the modal and the item
  flyout's Properties alike) shows everything the item holds and hides nothing: the built-ins (name,
  template, photo), the template's fields, and every other stored value as an editable Custom Fields
  row (`splitItemAttributes` in `lib/itemAttributes.ts`). Removing a row deletes that value; changing
  the template moves values between its fields and the rows rather than dropping or hiding any.
- **Tailwind:** class names must appear as full literal strings; never build them with `${}`
  interpolation (Tailwind cannot see them). Shared editor-bar styles are in
  `components/editorBarStyles.ts`.
- **Z-index:** never pick a `z-index` by guessing. `app/styles/Z_INDEX.md` maps every value in the
  app to what it's for and why, plus the stacking-context contract (transforms, filters, opacity
  and portals all change what a z-index can actually reach). A new stacking layer gets added there
  in the same commit, and the tree-menu/sidebar overlap it documents (menus render a few pixels
  *under* their own panel's edge) is intentional, not a bug to fix. While the pointer is over the template editor's
  bottom (footer) toolbar, it is lifted to the hover-raised layer (87) so it can be used even when an open flyout
  overlaps it, and drops back on leave so the flyout takes precedence again. Flyouts and the header are not raised on
  hover: a flyout stays tucked under its panel's edge.
- **Styling states:** controls are amber by default, white on hover and `--flyout-selected` yellow when
  selected / set; destructive hover uses the `--tree-menu-danger-*` variables. Use the shared class strings
  in `components/editorBarStyles.ts` (`activeBtn`, `barToggleOption`, ...) rather than writing new ones. The
  template editor toolbars have their own exceptions: see [docs/template-editor.md](docs/template-editor.md).

## Template editor

The full rules are in [docs/template-editor.md](docs/template-editor.md): read the part you need before
changing the editor, the layout engine, the gear flyouts or the item view.

- Every container is a Row or a Column; the Body is locked to Column. Templates are fluid, and zoom only
  scales the canvas visually: it never changes the layout.
- Layout edits are pure functions in `lib/layoutTree.ts` (tests: `tests/layout-tree.spec.ts`); selection and
  CRUD around them are in `hooks/useTemplateLayoutTree.ts`.
- Every gear flyout uses the one shell, `TreeSubMenu.tsx` / `TreeSubMenu.css`, in `splitBody` mode. Never
  add a second shell, a custom header class or a per-menu override.
- Editor-only state (zoom, preview width, hidden nodes, filters) is never saved into the layout.
- Undo / redo covers layout edits only, in memory. Field and template name / icon edits write straight
  to the database.
- **Testing the editor in a browser writes to the live database:** block non-GET requests to
  `item_templates` in Playwright scripts.

## Supabase access for Claude

- The project's `.mcp.json` runs Supabase's local MCP server **read-only**, scoped to this project
  (`--project-ref`), with the docs / database / debugging / development / functions tools (no account or branching
  tools). Its token is the `SUPABASE_ACCESS_TOKEN` environment variable, never stored in the repo. (The hosted
  server's sign-in rejects a URL carrying `project_ref` / `read_only`, which is why it isn't used.)
- A schema or data change is proposed and approved first, then made with read-only switched off for that job
  (remove `--read-only`, restart the session) and switched back on after; the change also goes into
  `.supabase/schema.sql` in the same commit.
- The live database also has Supabase's own `rls_auto_enable()` / `ensure_rls` event trigger (from the
  project setting that turns RLS on for every new `public` table). It is not part of `schema.sql`.

## Before accounts / production

- Replace the open development RLS policies with per-user policies when authentication is added, so
  templates and preferences belong to the person who made them.
- `.supabase/schema.sql` is the re-initialization script for a fresh Supabase project — it is not
  auto-generated from the live database. Any schema change (new table, column, index, constraint,
  RLS policy, or seed row) must be added to it in the same commit as the migration that makes the
  change, or the script silently drifts from reality (as was done for `layout_config`).

## Known state

- No authentication yet. The Row Level Security policies in `.supabase/schema.sql` are open
  development policies (public read/write); they must be replaced when accounts are added.
- The app is designed for wide desktop screens. Template building is not planned for phones.
